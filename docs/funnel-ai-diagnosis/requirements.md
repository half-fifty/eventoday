# 퍼널 기반 사용자 행동 분석 + AI 진단 — 요구사항

## 목적

Eventoday는 현재 티켓 구매 전환 흐름에서 사용자가 어느 단계까지 도달했다가 이탈하는지 알 수 없고,
설령 이탈 구간을 알더라도 그 원인이 UX/콘텐츠 문제인지 시스템 장애(느린 응답, 에러)인지 구분할 방법이 없다.

이 기능은 **전환 퍼널의 병목 구간을 정량적으로 찾고, 그 원인이 UX 문제인지 시스템 장애인지 구분해서
개최자·운영자가 대응 우선순위를 판단할 수 있게 하는 것**을 목적으로 한다.

(참고: 원래 ELK 스택 학습 목적에서 출발한 논의였으나, 위 문제 해결을 본 목적으로 재정의했다.
Elasticsearch/Kafka는 그 목적을 위한 구현 수단으로 채택했고, Kibana는 사용하지 않는다.)

## 범위

### 분석 대상 퍼널

실제 FE 코드 확인 결과, 부스 탐색(`/events/:eventId/ongoing`)은 티켓 구매(`EventDetail` 페이지 내 모달)의
필수 관문이 아니다 (라우팅상 완전히 독립). 따라서 핵심 구매 퍼널은 다음 3단계 + 방문으로 정의한다.

```
방문 → 행사상세 조회 → 티켓선택(구매모달 오픈) → 결제완료
```

- "티켓선택"은 별도 페이지 이동이 아니라 행사상세 페이지 내 모달 오픈이다.
- 부스 탐색은 핵심 퍼널에서 제외하고, "부스 탐색 여부"를 세션에 기록해 **부스를 본 세션과 안 본 세션의
  구매 전환율을 비교하는 별도 분석 축**으로만 사용한다.
- 각 단계의 판정 기준과 이벤트 계약은 `event-contract.md`, 집계 방식은 `technical-design.md` 참고.

### 분석 단위

- 퍼널은 행사(Event)별로 독립적으로 집계한다. 여러 행사의 데이터를 하나로 합친 전체 퍼널은 만들지 않는다.
  서로 다른 행사는 "정상 전환율" 기준 자체가 달라 합산하면 해석 불가능한 숫자가 되기 때문이다.
- 단, **운영자(Admin) 전용으로 행사별 리포트를 나란히 비교하는 뷰**는 별도 제공한다 (데이터를 합치는 게
  아니라 행사별로 이미 계산된 리포트를 병렬 조회하는 것 — 새 데이터 수집/스키마 변경 불필요).

## 기능 요구사항

- **비로그인 사용자 추적**: 비로그인 상태에서도 티켓 구매가 가능하므로, 로그인 여부와 무관하게 추적한다.
- **AI 진단**:
  - 하루 1회, 행사별 배치로 생성한다. 사용자가 대시보드를 열 때마다 실시간 호출하지 않는다.
  - 산출물은 정량적 진단 코멘트로 한정한다. 구체적 문구/이미지 개선안 생성은 이번 범위에서 제외한다.
    (예: "결제 선택 단계 이탈률이 평소보다 높습니다. 같은 시간대 결제 API 응답 지연과 관련 가능성이
    관찰되었습니다.")
  - AI는 이상탐지를 수행하는 주체가 아니라, 애플리케이션 코드가 이미 계산한 결과를 자연어로 설명하는
    계층이다. 인과관계를 단정하지 않는다.
- **콜드스타트/샘플 부족 처리**: 7일 미만 데이터가 쌓인 행사는 "평소 대비" 비교를 생략하고 수치 리포트만
  제공한다. 하루 방문(세션) 수가 임계치 미만이면 이상탐지 대상에서 제외한다.
- **열람 권한**:
  - 플랫폼 운영자(Admin): 모든 행사의 리포트 + 행사 간 비교 뷰 조회 가능.
  - 개최자(Organization): 본인이 개최한 행사의 리포트만 조회 가능 (`Organization`↔`EventOrganization`
    관계 재사용).
- **Kibana 미사용**: 리포트 조회 화면은 Kibana가 아니라 Eventoday 기존 FE/BE에 자체 페이지로 구현한다.
  Kibana를 쓰면 기존 인증/인가 체계(운영자/개최자 구분)를 재사용할 수 없어 별도 인증 체계가 필요해지고,
  이는 현재 권한 모델과 맞지 않는다.

## 우선순위

### P0: 필수

- 이벤트 계약 정의 및 수집 파이프라인 (`event-contract.md` 참고)
- 일일 배치: 원본 액션 → `FunnelSession` 재구성 (도달/이탈/부스탐색여부/단계건너뜀 계산)
- 행사별 수치 기반 대시보드 (전환율, 부스탐색 여부별 비교)
- 대시보드 열람 권한 분리: 운영자(전체) / 개최자(본인 행사만)
- 결제 도메인과의 인터페이스 합의 (`event-contract.md`의 "결제 도메인과 사전 합의 필요 사항" 참고)

### P0.5: 이상탐지

- 통계적 이상탐지 (7일 이동평균 + 절대/상대 차이 + 2-proportion 검정)
- 시스템 로그 상관 조회 (endpoint/오류율/p95/결제실패율)
- 수치 기반 템플릿 진단 리포트 (LLM 없이)

### P1: AI 및 확장

- LLM 진단 코멘트 연동 (JSON 스키마 제한, 템플릿 폴백)
- 운영자 전용 행사 간 비교 뷰
- 판정 기준값(세션 윈도우, 이동평균 기간, 샘플 임계치)을 설정값으로 분리

### P2: 후속 검토

- 실시간 알림(Slack/Email) 연동
- 부스 신청 퍼널로 확장
- 문구/이미지 구체적 개선안 생성 (현재 범위에서 명시적으로 제외됨)

## 구현 전 확인할 결정사항

- [ ] 결제 도메인 Outbox가 발행하는 메시지의 최종 스키마/토픽명 — 담당 팀원과 실제 합의 완료 필요
      (초안은 `event-contract.md` 참고)
- [ ] LLM 어떤 모델/API를 쓸지 (Claude API 등) 결정
- [ ] 세션 윈도우 30분, 이동평균 7일, 이상탐지 임계치 — 초기값으로 확정할지, 설정값으로 미리 빼둘지
- [ ] 개최자 조직에 소속된 멤버 중 누구까지 리포트를 볼 수 있는지 (OWNER만? MANAGER/STAFF도?) —
      기존 `EventRole` 정책 재사용 여부 확인 필요

결정되지 않은 항목 때문에 P0 구현을 임의로 확대하지 않는다.
